# 미용실 예약 시스템 기획안 (v0.2 확정)

> 작성일: 2026-07-04
> 상태: **확정 — 구현 진행 중**
>
> ### 확정된 결정사항 (오픈 질문 답변)
> 1. 대상: **특정 매장 1곳** (제품화 아님)
> 2. 예약금 결제: **2차로 연기** (MVP는 3단계 리마인드로 노쇼 방어)
> 3. 알림 채널: **카카오톡 챗봇 채널 기반** (알림톡/SMS는 2차)
> 4. 코드 위치: **이 레포에 통합** (`booking/` 모듈)
> 5. 매장 형태: **1인샵** → 디자이너 선택 단계·디자이너 테이블 생략, 예약 흐름은
>    "시술 선택 → 시간 선택"으로 단순화
> 6. (추가) 회원: 아이디/비밀번호 가입은 도입하지 않고 **카카오/네이버 간편
>    로그인**만 선택적으로 제공. 비회원 예약(예약번호+전화번호)은 그대로 유지,
>    로그인 시 예약번호 없이 "내 예약" 자동 조회
> 7. (추가) 사진 기록: 고객은 예약 시 **원하는 스타일 사진(최대 3장)** 첨부 가능,
>    원장은 시술 후 **정면/측면/뒷면 결과 사진** 기록(각도당 1장, 재업로드 시 교체).
>    사진은 본인과 관리자만 열람 가능. 촬영 전 고객 동의는 운영 원칙으로 준수

## 1. 목표

단일 미용실(1개 매장)을 위한 **예약 웹앱**을 만든다. 대형 플랫폼(카카오헤어샵, 네이버 예약)의
장점은 흡수하되, 플랫폼 수수료 없이 매장이 직접 운영하는 자체 예약 채널을 목표로 한다.
기존에 운영 중인 카카오톡 챗봇(이 레포의 웹훅 서버)과 연계해 **카카오톡으로 예약 접수·리마인드
알림**을 보내는 것을 차별화 포인트로 삼는다.

## 2. 벤치마킹 요약

기존 서비스들을 조사한 결과, 잘 만들어진 시스템들의 공통 스킬(기능)은 다음과 같다.

| 서비스 | 핵심 스킬 | 참고할 점 |
|---|---|---|
| **카카오헤어샵** | 전액 선결제, 시술 30분 전까지 100% 환불 | 선결제 덕에 **노쇼율 1% 미만**. 단, 수수료가 높아(예약 건당 최대 25% 수준) 매장 이탈이 많았음 |
| **네이버 예약(스마트플레이스)** | 예약금(보통 1만원) 선결제, 낮은 수수료(결제 시 최대 2.9%, 예약만 하면 0원) | 국내 사용자에게 가장 익숙한 예약 UX. 예약금 모델이 사실상 국내 표준 |
| **Fresha** | 카드 등록 후 노쇼/지각취소 수수료 자동 청구, 이메일·SMS 자동 리마인드, 유연한 취소 정책 설정 | 노쇼 방어 기능이 모든 요금제에 기본 포함 — "노쇼 방어는 옵션이 아니라 기본"이라는 방향성 |
| **Booksy** | 마켓플레이스 기반 신규 고객 유입, 디자이너별 프로필/포트폴리오 | 디자이너 개인 단위 브랜딩·지명 예약 UX |
| **국내 살롱 SaaS (노쇼없는미용실 등)** | 예약 리마인드, 시술시간 기록, 디자이너별 예약 간격 추천 | 시술 소요시간 데이터 축적 → 예약 슬롯 정확도 개선이라는 운영 노하우 |

## 3. 고객 민감 포인트 분석 (핵심 설계 기준)

리서치 결과, 미용실 고객이 가장 민감해하는 것은 아래 5가지다. 이 기획안의 모든 기능은
이 5가지를 해결하는 데 초점을 맞춘다.

### P1. 예약했는데 기다리게 되는 것 (대기시간)
- 예약 시간에 방문해도 앞 손님 시술이 밀려 15분 이상 대기하는 경험이 대표적 불만.
- **해결 설계**: 시술 메뉴별 표준 소요시간을 정의하고, 디자이너별 실제 소요시간을 기록해
  슬롯 간격을 현실화한다. 예약이 밀릴 경우 고객에게 사전 지연 알림(카카오톡)을 보낸다.

### P2. 노쇼·당일취소 (매장 측 민감 포인트이자 정책의 핵심)
- 국내 표준은 "예약금 선결제": 네이버는 1만원 예약금, 카카오는 전액 선결제 모델이었다.
- **해결 설계**: MVP에서는 예약금 없이 시작하되(결제 연동은 2차), **예약 확정 → 전날 리마인드
  → 당일 아침 리마인드**의 3단계 카카오톡 알림으로 노쇼를 줄인다. 2차에서 토스페이먼츠 등으로
  예약금 결제를 붙인다.

### P3. 원하는 디자이너 지명
- "그 디자이너에게 받고 싶다"는 지명 요청은 당연한 요구로 인식된다.
- **해결 설계**: 예약 흐름을 **디자이너 선택 → 시술 선택 → 시간 선택** 순서로 설계.
  디자이너별 프로필(경력, 전문 시술, 스타일 사진)과 개인별 예약 캘린더를 제공한다.

### P4. 가격 투명성
- 방문 후 "기장 추가", "제품 추가"로 가격이 붙는 경험에 대한 불신이 크다.
- **해결 설계**: 메뉴에 기본가 + 추가금 조건(기장, 상태)을 명시하고, 예약 시점에
  예상 가격 범위를 확정해 보여준다.

### P5. 취소·변경의 번거로움
- 전화해야만 취소/변경이 되는 시스템은 오히려 노쇼를 유발한다.
- **해결 설계**: 예약 조회/변경/취소를 웹에서 셀프로 처리. 취소 정책(예: 24시간 전까지 무료)을
  예약 시점에 명시하고 정책 위반 취소는 매장에 즉시 알림.

## 4. 제품 컨셉

```
[고객]  모바일 웹앱 (예약/조회/변경)  ←→  [예약 API 서버 (FastAPI, 이 레포 확장)]
[고객]  카카오톡 챗봇 (기존 웹훅)      ←→        │  ├ 예약 엔진 (슬롯 계산/충돌 방지)
                                                │  ├ 알림 엔진 (리마인드 스케줄러)
[원장/디자이너]  관리자 웹 (일정/메뉴/고객 관리) ←┘  └ DB (SQLite → PostgreSQL)
```

- **고객용**: 앱 설치 없는 모바일 웹. 카카오톡 채널 메뉴/챗봇에서 링크로 진입.
- **관리자용**: 원장이 쓰는 캘린더 중심 화면. 디자이너별 일정, 수기 예약(전화 예약) 입력 포함.
- **챗봇 연계**: 기존 Claude 챗봇이 "예약하고 싶어요" 의도를 감지하면 예약 웹앱 링크를 응답,
  예약 확정/리마인드는 카카오톡 알림으로 발송.

## 5. 기능 명세

### MVP (1차)
| # | 기능 | 상세 | 민감 포인트 |
|---|---|---|---|
| 1 | 시술 메뉴 관리 | 카테고리(컷/펌/염색/클리닉), 기본가, 추가금 조건, 표준 소요시간 | P4 |
| 2 | 디자이너 관리 | 프로필, 근무시간, 휴무, 시술 가능 메뉴 | P3 |
| 3 | 예약 생성 | 디자이너 → 메뉴 → 날짜/시간 선택. 가용 슬롯만 노출, 동시 예약 충돌 방지 | P1, P3 |
| 4 | 예약 조회/변경/취소 | 전화번호 + 인증(간단 OTP 또는 예약번호)으로 셀프 관리 | P5 |
| 5 | 취소 정책 표시 | 예약 시점에 정책 고지, 마감 시간 이후 취소는 매장 알림 | P2, P5 |
| 6 | 관리자 캘린더 | 일/주 단위 디자이너별 예약 현황, 수기 예약 입력, 예약 상태 변경(방문/노쇼) | P1, P2 |
| 7 | 리마인드 알림 | 예약 확정 즉시 + 전날 저녁 + 당일 아침, 카카오톡(챗봇 채널) 또는 SMS | P2 |

### 2차 (MVP 검증 후)
- 예약금 결제 연동 (토스페이먼츠) + 노쇼 시 예약금 정책 자동 적용 — P2 완성
- 디자이너별 실제 시술시간 기록 → 슬롯 간격 자동 보정 — P1 고도화
- 지연 발생 시 대기 고객 사전 알림 — P1 고도화
- 고객 히스토리(시술 이력, 선호 스타일 메모) 및 재방문 주기 알림
- 리뷰/포트폴리오 (디자이너별 스타일 사진)

### 명시적으로 안 하는 것 (MVP 범위 밖)
- 다중 매장 지원, 마켓플레이스(매장 검색·노출)
- 네이티브 앱 (모바일 웹으로 충분)
- POS/재고/급여 관리

## 6. 화면 구성 (고객용 웹앱)

1. **홈**: 매장 소개, "예약하기" CTA, 내 예약 조회
2. **디자이너 선택**: 프로필 카드(사진/경력/전문 분야), "아무나 괜찮아요" 옵션
3. **메뉴 선택**: 가격·소요시간·추가금 조건 명시 (P4)
4. **날짜/시간 선택**: 가용 슬롯 캘린더 (선택한 디자이너 + 메뉴 소요시간 기준으로 계산)
5. **정보 입력 & 확인**: 이름/전화번호/요청사항 + 취소 정책 동의
6. **완료**: 예약번호 발급, 카카오톡 확정 알림
7. **내 예약**: 조회/변경/취소

관리자 화면: 캘린더(일/주), 예약 상세(상태 변경), 메뉴 관리, 디자이너 관리, 영업시간/휴무 설정.

## 7. 데이터 모델 (초안)

```
Shop        : id, name, 영업시간, 휴무일, 취소정책(마감시간)
Designer    : id, shop_id, 이름, 프로필, 근무스케줄, 휴무
Service     : id, 이름, 카테고리, 기본가, 추가금조건(텍스트), 소요시간(분)
DesignerService : designer_id, service_id  (디자이너별 가능 시술)
Customer    : id, 이름, 전화번호, 카카오유저ID(챗봇 연계용, nullable)
Reservation : id, customer_id, designer_id, service_id, 시작시각, 종료시각,
              상태(대기/확정/방문완료/노쇼/취소), 요청사항, 예상가격, 생성경로(웹/챗봇/수기)
Notification: id, reservation_id, 타입(확정/전날/당일/지연), 발송시각, 상태
```

## 8. 기술 스택

- **백엔드**: FastAPI (이 레포 확장 또는 별도 앱), SQLModel/SQLAlchemy
- **DB**: SQLite로 시작 → PostgreSQL 전환 (현재 레포의 in-memory 방식은 예약에는 부적합)
- **프론트**: 서버 렌더링(Jinja2) + 경량 JS 로 시작 — 모바일 웹 중심, 빌드 파이프라인 최소화.
  화면 복잡도가 올라가면 React 전환 검토
- **알림**: 1차는 카카오톡 챗봇 채널 활용, 카카오 알림톡(비즈메시지)은 사업자 심사 필요하므로 2차
- **예약 충돌 방지**: DB 트랜잭션 + 유니크 제약 (디자이너/시간대)

## 9. 검증 계획 (CLAUDE.md 원칙 적용)

각 단계별 완료 기준:

1. 데이터 모델 + 슬롯 계산 로직 → 검증: 경계 케이스 테스트(영업시간 밖, 겹치는 예약, 휴무일)
2. 예약 API → 검증: httpx로 동시 예약 요청 시 충돌 방지 확인
3. 고객 웹 플로우 → 검증: 모바일 뷰포트에서 예약 생성~취소 전 과정 수동 테스트
4. 챗봇 연계 → 검증: 기존 `/kakao/webhook`에 예약 의도 발화 curl 테스트
5. 리마인드 스케줄러 → 검증: 시간 조작 테스트로 3단계 알림 발송 확인

## 11. 오픈 질문 (시작 전 결정 필요)

1. **대상 매장**: 실제 운영 중인 특정 미용실용인가, 아니면 여러 미용실에 팔 수 있는 제품인가?
   → MVP 설계가 달라짐 (이 기획안은 단일 매장 가정)
2. **예약금**: MVP부터 결제(예약금)를 넣을 것인가? (결제 연동은 개발량이 크게 늘어남 — 2차 권장)
3. **알림 채널**: 카카오톡 챗봇 채널로 충분한가, 알림톡/SMS까지 필요한가?
4. **이 레포와의 관계**: 기존 웹훅 서버에 통합(모노레포)할 것인가, 별도 프로젝트로 새로 팔 것인가?
5. **디자이너 수**: 1인샵인가 다인샵인가? (1인샵이면 디자이너 선택 단계를 생략해 UX가 단순해짐)
