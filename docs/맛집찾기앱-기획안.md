# 맛집찾기 앱 기획서 (가칭: 진짜맛집)

**버전:** v0.1 (초안) · **작성일:** 2026-08-13
**핵심 콘셉트:** 인스타그램 · 유튜브 · 검색(블로그/뉴스)을 **교차검증**해서 "광고가 아닌 진짜 맛집"만 골라주는 앱

---

## 1. 문제 정의 — 왜 이 앱인가

- 네이버·구글 평점은 리뷰 이벤트, 광고성 블로그 때문에 신뢰도가 낮다.
- 인스타에서 핫한 곳 ≠ 유튜버가 인정한 곳 ≠ 블로그 후기가 좋은 곳. **셋이 겹치는 곳이 진짜다.**
- 막상 찾아가면 브레이크타임이거나 라스트오더가 지나서 헛걸음하는 경우가 많다.
- 예약 가능 여부, 가격대를 한 화면에서 확인할 수 있는 서비스가 드물다.

**한 줄 가치 제안:** "세 개의 채널이 동시에 인정한 맛집만, 지금 갈 수 있는 곳으로 보여준다."

## 2. 핵심 기능 요약

| # | 기능 | 설명 |
|---|------|------|
| 1 | 카테고리 분류 | 한식 / 중식 / 일식 / 양식(이탈리안) / 아시안 / 카페·디저트 / 술집·바 |
| 2 | 지역 자유 검색 | 지역명·역명·동명 입력 → 해당 지역 반경 내 검색 |
| 3 | 교차검증 랭킹 | 인스타 + 유튜브 + 블로그/검색 데이터를 점수화해 종합 랭킹 |
| 4 | 가격대 필터 | ₩ (1만 미만) / ₩₩ (1~3만) / ₩₩₩ (3~7만) / ₩₩₩₩ (7만 이상) |
| 5 | 예약 확인 | 네이버예약·캐치테이블 지원 여부 표시 + 바로가기 연결 |
| 6 | 영업 상태 | 브레이크타임 / 라스트오더 / "지금 가면 먹을 수 있는지" 실시간 표시 |

## 3. 카테고리 체계

대분류 7개 + 소분류(필터용)로 설계한다. 카카오 로컬 API의 음식점 카테고리 코드(FD6)와 매핑 가능하다.

- **한식** — 국밥·찌개, 고기·구이, 횟집·해산물, 분식, 백반·정식
- **중식** — 중화요리, 마라·훠궈, 딤섬
- **일식** — 스시·오마카세, 라멘·우동, 돈카츠·규동, 이자카야
- **양식** — 이탈리안(파스타·피자), 스테이크·버거, 브런치
- **아시안** — 베트남, 태국, 인도
- **카페·디저트** — 베이커리, 브런치카페, 디저트 전문
- **술집·바** — 와인바, 위스키바, 포차·펍

## 4. 교차검증 알고리즘 (이 앱의 심장)

### 4.1 기본 아이디어

한 채널에서만 뜨는 가게는 광고일 확률이 높다. **서로 성격이 다른 세 채널에서 동시에 언급되는 가게**는 조작이 어렵다. 이를 점수로 만든다.

### 4.2 채널별 신호 수집

| 채널 | 수집 신호 | 수집 방법 |
|------|-----------|-----------|
| 검색(블로그) | 최근 6개월 리뷰 수, 긍정 표현 비율, "내돈내산" 언급, "협찬" 언급(감점) | 네이버 검색 API (블로그·카페·웹문서) |
| 유튜브 | 가게명 언급 영상 수, 조회수 합, 채널 신뢰도(구독자), "광고 포함" 표기(감점) | YouTube Data API |
| 인스타그램 | 해시태그 게시물 수, 최근 게시 빈도 | 공식 API 제약이 커서 간접 수집(아래 6장 참고) |
| 지도 평점 | 평점, 리뷰 수 | 카카오·네이버 지역 검색 결과 |

### 4.3 종합 점수 산식 (초안)

```
종합점수 = (블로그점수 × 0.35) + (유튜브점수 × 0.30)
         + (인스타점수 × 0.20) + (평점점수 × 0.15)

교차검증 보너스: 3개 채널 모두 기준치 이상이면 ×1.2
광고 페널티: "협찬/광고/유료광고" 비율이 30% 넘으면 ×0.7
신선도 가중: 최근 3개월 언급이 없으면 ×0.8 (폐업·하락 가능성)
```

각 채널 점수는 지역 내 상대평가(백분위)로 정규화해서 0~100점으로 만든다. 이렇게 하면
강남과 소도시를 같은 기준으로 비교하는 오류를 피할 수 있다.

### 4.4 결과 등급 표시

- 🏆 **교차검증 맛집** — 3개 채널 모두 통과 (핵심 차별점)
- ✅ **검증 맛집** — 2개 채널 통과
- 📌 **후보** — 1개 채널에서만 확인됨

## 5. 화면 설계 (5개 화면)

### ① 홈 / 검색

- 상단: 지역 검색창 ("성수동", "강남역" 등 자유 입력)
- 카테고리 7개 아이콘 가로 배치
- 하단: 현재 위치 기반 "지금 갈 수 있는 근처 교차검증 맛집" 3곳

### ② 검색 결과 (리스트)

- 정렬: 종합점수순(기본) / 평점순 / 거리순
- 필터 바: 가격대 · 예약 가능 · **"지금 영업 중"** · "1시간 내 라스트오더 아님"
- 카드 구성: 가게명 · 등급 배지 · 카테고리 · 가격대 · 평점 · 영업 상태(🟢영업중 /
  🟡브레이크타임 14:30~17:00 / 🔴라스트오더 임박 / ⚫영업종료)

### ③ 가게 상세

- 교차검증 리포트: "블로그 후기 128건 · 유튜브 영상 6개 · 인스타 게시물 2,400건" —
  **근거를 보여주는 게 신뢰의 핵심**
- 대표 유튜브 영상·블로그 링크 바로가기
- 영업시간 표: 요일별 + 브레이크타임 + 라스트오더
- 예약: 네이버예약/캐치테이블 버튼 (딥링크 이동)
- 가격대 + 대표 메뉴 가격

### ④ 필터 상세 (바텀시트)

- 가격대 4단계, 예약 가능 여부, 영업 상태, 소분류 카테고리

### ⑤ 저장 / 마이

- 찜 목록, 가봤어요 기록, "다녀왔는데 별로였어요" 피드백 (알고리즘 보정에 활용)

## 6. 데이터 소스 — 현실적인 제약과 해법

기획에서 가장 중요한 부분이다. 조사 결과, 각 채널의 공식 API 상황이 다음과 같다.

### 6.1 사용 가능한 것 (바로 연동 가능)

- **카카오 로컬 API** — 키워드·카테고리(음식점 FD6) 장소 검색, 좌표, 주소, 전화번호.
  무료 쿼터 넉넉함. **지역 검색의 뼈대**로 사용.
- **네이버 검색 API** — 블로그·카페·지역 검색. 블로그 리뷰 수와 본문 스니펫으로
  교차검증의 핵심 신호를 얻는다. 단, 지역 검색은 쿼리당 결과 5건 제한이 있어
  "가게 발굴"은 카카오, "후기 검증"은 네이버로 역할 분담.
- **YouTube Data API** — 가게명+지역명 검색으로 관련 영상·조회수 수집. 일일 쿼터
  (10,000 유닛, 검색 1회당 100 유닛)가 있어 캐싱 필수.

### 6.2 제약이 큰 것 (우회 전략 필요)

- **인스타그램** — 해시태그 검색 API는 비즈니스 계정 인증 + 7일간 30개 해시태그
  제한이라 실시간 검색용으로는 사실상 못 쓴다.
  → **해법:** 네이버/구글 웹 검색 결과에서 인스타그램 게시물 인덱스를 세는 간접 방식 +
  해시태그 게시물 수는 배치(하루 1회)로만 갱신.
- **예약 여부 (네이버예약·캐치테이블)** — 둘 다 공개 예약 API가 없다.
  → **해법:** 예약 페이지 존재 여부만 확인해서 "예약 가능" 배지를 붙이고, 실제 예약은
  해당 앱/페이지로 딥링크 연결. (예약 대행이 아니라 "예약 가능 여부 확인 + 연결"로
  기능을 정의 — 사용자 요구와도 일치)
- **브레이크타임·라스트오더** — 카카오·네이버 API 모두 영업시간을 안 준다.
  → **해법 3단계:** ① 구글 Places API의 영업시간 데이터로 기본값 확보 → ② 네이버
  플레이스에 공개된 정보를 배치 수집해 브레이크타임·라스트오더 보강 → ③ 사용자
  제보("브레이크타임이 바뀌었어요")로 보정. 라스트오더는 데이터가 가장 귀하므로
  **초기엔 사용자 제보 + 운영자 입력 중심**으로 시작하는 게 현실적.

### 6.3 데이터 파이프라인

```
[배치 수집기 (하루 1~2회)]
  카카오 로컬 → 지역별 가게 목록 확보
  → 가게별로 네이버 블로그 검색 / 유튜브 검색 / 인스타 간접 수집
  → 교차검증 점수 계산 → DB 저장

[실시간 (사용자 요청 시)]
  DB 조회 + 영업 상태 계산(현재 시각 vs 영업시간표)
  → 캐시에 없는 신규 지역이면 즉석 수집 후 "분석 중" 표시
```

## 8. 기술 스택 제안

| 영역 | 선택 | 이유 |
|------|------|------|
| 앱 | React Native (Expo) | iOS·안드로이드 동시 대응, 웹 프로토타입과 코드 감각 공유 |
| 백엔드 | Python (FastAPI) | 수집·점수계산 로직에 파이썬 생태계가 유리 |
| DB | PostgreSQL + PostGIS | 위치 기반 반경 검색 |
| 배치 | 스케줄러(cron) + 수집 워커 | API 쿼터 관리, 캐싱 |
| 캐시 | Redis | 지역별 검색 결과 캐싱으로 API 비용 절감 |

## 9. 개발 로드맵

### Phase 1 — MVP (핵심 검증)

- 지역 검색 + 카테고리 + 카카오/네이버/유튜브 3채널 교차검증 점수
- 가격대 필터, 영업시간은 구글 Places 기본값
- 웹앱 프로토타입으로 화면·알고리즘 검증

### Phase 2 — 차별화 기능

- 브레이크타임·라스트오더 DB 구축(수집+제보), "지금 갈 수 있는 곳" 필터
- 예약 가능 배지 + 딥링크
- 인스타 간접 수집 고도화

### Phase 3 — 앱 출시

- React Native 앱 패키징, 푸시("찜한 가게 라스트오더 1시간 전"), 사용자 피드백
  루프로 점수 보정

## 10. 리스크와 대응

- **API 쿼터·비용** — 유튜브·구글 쿼터 한계 → 배치 수집 + 캐싱으로 사용자 요청과
  API 호출을 분리 (구조에 이미 반영)
- **크롤링 정책** — 네이버 플레이스 등 배치 수집 시 robots.txt·약관 검토 필요.
  공식 API 우선, 수집은 최소화
- **데이터 신선도** — 폐업·시간 변경 감지 → 신선도 가중치 + 사용자 제보
- **콜드 스타트** — 처음엔 데이터가 없다 → 인기 지역(강남·성수·홍대 등)부터 미리
  수집해두고, 신규 지역은 "분석 중 → 몇 분 후 완성" UX로 해결
